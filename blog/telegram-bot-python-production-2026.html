Building a Telegram Bot with Python: From Zero to Production

2026-07-11 · 14 min read · by xbyteid
PythonTelegramBotAutomation

Building a Telegram bot in 2026 is one of the fastest ways to ship a useful tool. Whether it's a trading alert bot, a customer support agent, or an AI assistant, Python + python-telegram-bot gives you the shortest path from idea to production. I've built and maintained multiple bots handling thousands of messages daily — here's what actually works.

Choosing Your Stack

There are two main Python libraries for Telegram bots:

  • python-telegram-bot (PTB) — the most popular, async-first, excellent documentation, built-in job queue. Best for most projects.
  • aiogram — lighter, faster, more Pythonic for advanced users. Better for high-throughput bots.
  • Telethon / Pyrogram — these are Telegram client libraries (userbot), not Bot API. Use only if you need to act as a real user account.

For 90% of use cases, python-telegram-bot is the right choice. The v20+ async API is clean, the community is large, and the built-in rate limiting saves you from hitting Telegram's API limits.

Webhook vs Polling

This is the first architectural decision you'll make:

  • Polling — your bot continuously asks Telegram "any new messages?" Simple, works behind NAT, no public URL needed. Fine for development and small bots.
  • Webhook — Telegram pushes updates to your server via HTTPS. Lower latency, more efficient, required for production. Needs a public URL with valid SSL.

For production, always use webhooks. Polling wastes resources and has inherent latency. Here's the webhook setup with PTB:

from telegram import Update
from telegram.ext import Application, CommandHandler, MessageHandler, filters

async def start(update: Update, context):
    await update.message.reply_text(f"Hello {update.effective_user.first_name}!")

async def handle_message(update: Update, context):
    text = update.message.text
    if text == "/ping":
        await update.message.reply_text("pong")
    elif "/price" in text:
        token = text.split()[-1] if len(text.split()) > 1 else "ETH"
        # Your price fetching logic here
        await update.message.reply_text(f"{token}: $3,450.00")

app = Application.builder().token("BOT_TOKEN").build()
app.add_handler(CommandHandler("start", start))
app.add_handler(MessageHandler(filters.TEXT & ~filters.COMMAND, handle_message))

# Production webhook
app.run_webhook(
    listen="0.0.0.0",
    port=8443,
    url_path="webhook",
    webhook_url="https://yourdomain.com/webhook"
)

Building Real Features

Inline Keyboards

Buttons make bots interactive. Here's a callback-driven menu:

from telegram import InlineKeyboardButton, InlineKeyboardMarkup

async def menu(update, context):
    keyboard = [
        [InlineKeyboardButton("📊 Portfolio", callback_data="portfolio"),
         InlineKeyboardButton("🔔 Alerts", callback_data="alerts")],
        [InlineKeyboardButton("⚙️ Settings", callback_data="settings")]
    ]
    reply = InlineKeyboardMarkup(keyboard)
    await update.message.reply_text("Choose:", reply_markup=reply)

async def button_callback(update, context):
    query = update.callback_query
    await query.answer()
    if query.data == "portfolio":
        await query.edit_message_text("Loading portfolio...")
    elif query.data == "alerts":
        await query.edit_message_text("Alert settings...")

File Handling

Bots can send and receive files — useful for reports, screenshots, exports:

async def handle_document(update, context):
    file = await update.message.document.get_file()
    path = await file.download_to_drive("downloads/uploaded.csv")
    await update.message.reply_text(f"Received {update.message.document.file_name}")

async def send_report(update, context):
    # Generate and send a file
    with open("report.pdf", "rb") as f:
        await update.message.reply_document(document=f, filename="daily_report.pdf")

Production Deployment

Running a bot on a VPS with systemd ensures it restarts on crash and starts on boot:

# /etc/systemd/system/mybot.service
[Unit]
Description=Telegram Bot
After=network.target

[Service]
Type=simple
User=botuser
WorkingDirectory=/opt/mybot
ExecStart=/opt/mybot/venv/bin/python main.py
Restart=always
RestartSec=10
Environment=BOT_TOKEN=your_token_here

[Install]
WantedBy=multi-user.target

Then: sudo systemctl enable --now mybot

Reverse Proxy with Nginx

For webhook bots, put Nginx in front for SSL termination and rate limiting:

server {{
    listen 443 ssl;
    server_name bot.yourdomain.com;

    ssl_certificate /etc/letsencrypt/live/bot.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/bot.yourdomain.com/privkey.pem;

    location /webhook {{
        proxy_pass http://127.0.0.1:8443;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }}
}}

Error Handling and Logging

Telegram bots crash silently without proper error handling. Always add:

import logging
logging.basicConfig(
    format='%(asctime)s - %(name)s - %(levelname)s - %(message)s',
    level=logging.INFO,
    handlers=[
        logging.FileHandler('bot.log'),
        logging.StreamHandler()
    ]
)

async def error_handler(update, context):
    logging.error(f"Exception: {context.error}", exc_info=context.error)
    if update and update.effective_message:
        await update.effective_message.reply_text("Something went wrong. Try again.")

Rate Limiting

Telegram limits bots to ~30 messages/second globally, and ~20 messages/minute per chat. Use the built-in rate limiter:

from telegram.ext import Defaults

defaults = Defaults(
    rate_limiter=AIORateLimiter(
        overall_max_rate=30,
        overall_time_period=1,
        group_max_rate=20,
        group_time_period=60
    )
)
app = Application.builder().token("TOKEN").defaults(defaults).build()

Real-World Patterns

Conversation Flow

For multi-step interactions (onboarding, forms), use ConversationHandler:

from telegram.ext import ConversationHandler

NAME, EMAIL = range(2)

async def ask_name(update, context):
    await update.message.reply_text("What's your name?")
    return NAME

async def get_name(update, context):
    context.user_data['name'] = update.message.text
    await update.message.reply_text("And your email?")
    return EMAIL

async def get_email(update, context):
    context.user_data['email'] = update.message.text
    await update.message.reply_text(f"Thanks {{context.user_data['name']}}!")
    return ConversationHandler.END

conv = ConversationHandler(
    entry_points=[CommandHandler("register", ask_name)],
    states={{
        NAME: [MessageHandler(filters.TEXT & ~filters.COMMAND, get_name)],
        EMAIL: [MessageHandler(filters.TEXT & ~filters.COMMAND, get_email)]
    }},
    fallbacks=[CommandHandler("cancel", cancel)]
)

Persistent Data

Store user data across restarts with PicklePersistence or a database:

from telegram.ext import PicklePersistence

persistence = PicklePersistence(filepath="bot_data.pickle")
app = Application.builder().token("TOKEN").persistence(persistence).build()

# Now context.user_data persists across restarts
async def set_alert(update, context):
    context.user_data.setdefault('alerts', []).append(update.message.text)
    await update.message.reply_text("Alert saved!")
Pro tip: Use context.bot_data for shared state across all users (like cached prices), and context.user_data for per-user state. Don't store sensitive data in pickle files — use a proper database (SQLite for small bots, PostgreSQL for production).

Monitoring

Set up a health check endpoint and uptime monitoring:

from aiohttp import web

async def health(request):
    return web.Response(text="ok")

# Run alongside your bot
health_app = web.Application()
health_app.router.add_get('/health', health)
web.run_app(health_app, port=8080)

Use UptimeRobot or a simple cron to ping https://bot.yourdomain.com/health every minute. Get Telegram alerts when the bot goes down.

What I've Learned

After running multiple Telegram bots in production, here are the lessons:

  • Always use webhooks in production — polling is wasteful and unreliable at scale
  • Log everything — when a user reports a bug, logs are your only evidence
  • Handle rate limits gracefully — queue messages instead of dropping them
  • Use inline keyboards — buttons are 10x better UX than free text for structured interactions
  • Deploy with systemd — not screen/tmux/nohup. Systemd handles restarts, logging, and boot persistence
  • Test with a private group first — create a test group with your bot before going to production
