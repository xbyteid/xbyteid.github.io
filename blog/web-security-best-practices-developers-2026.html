Web Security Best Practices for Developers in 2026

2026-06-24·14 min read·by xbyteid
SecurityWeb DevOWASPBest Practices

Why Security Can't Wait

Every 39 seconds, a web application is attacked. In 2026, the average cost of a data breach exceeds $5 million. Yet most breaches exploit well-known vulnerabilities with well-known fixes. The OWASP Top 10 hasn't changed dramatically in years — the problem isn't knowledge, it's execution. This guide covers the security practices every developer should implement from day one.

XSS Prevention

Cross-Site Scripting (XSS) remains the #1 web vulnerability. Attackers inject malicious scripts into pages viewed by other users, stealing session tokens, redirecting to phishing sites, or defacing content. The fix: never trust user input, always encode output.

// DANGEROUS — never do this
element.innerHTML = userInput;

// SAFE — use textContent for plain text
element.textContent = userInput;

// SAFE — use DOMPurify for rich HTML
import DOMPurify from 'dompurify';
element.innerHTML = DOMPurify.sanitize(userInput);

Types of XSS

Stored XSS — malicious input saved to the database and rendered to other users (comments, profile bios, forum posts). This is the most dangerous type because it affects every user who views the page.

Reflected XSS — malicious input in a URL parameter rendered back into the page without sanitization. Attackers send crafted links via email or social media.

DOM-based XSS — client-side JavaScript reads attacker-controlled input (URL hash, postMessage, document.referrer) and writes it to the DOM unsafely.

Framework-Level Protection

Modern frameworks auto-escape by default: React escapes JSX expressions, Vue escapes template interpolations, Angular sanitizes bindings. The danger zones are:

// React — DANGEROUS (bypasses escaping)
<div dangerouslySetInnerHTML={{ __html: userInput }} />

// Vue — DANGEROUS
<div v-html="userInput" />

// Angular — bypasses sanitizer
<div [innerHTML]="userInput" [trustedHtml]="true" />

Only use these when the content has been sanitized by DOMPurify or a server-side sanitizer. Never pass raw user input to these APIs.

On the server side, use template engines with auto-escaping enabled (Jinja2, Razor, Go templates). Disable auto-escaping only when you explicitly sanitize the content.

Content Security Policy (CSP)

CSP is your second line of defense against XSS. It tells the browser which sources of content are allowed, blocking inline scripts and untrusted domains:

Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-abc123'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; connect-src 'self' https://api.yourdomain.com

For nginx:

server {
    add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'nonce-$request_id';" always;
}

Start with Content-Security-Policy-Report-Only to test without breaking anything, then enforce once you've whitelisted all legitimate sources.

CSP Nonce Strategy

Nonces are single-use random values embedded in your CSP header and each <script> tag. The browser only executes scripts with a valid nonce — injected scripts without one are blocked:

<!-- In your HTML template -->
<script nonce="{{ nonce }}">
  // Your legitimate inline script
</script>

<!-- Attacker-injected script — BLOCKED (no nonce) -->
<script>alert('xss')</script>

Generate a fresh nonce per request in your backend middleware. For Next.js, libraries like next-csp handle this automatically. For Express, use helmet-csp.

CSRF Protection

Cross-Site Request Forgery tricks users into making unwanted requests. Protect state-changing endpoints (POST, PUT, DELETE) with CSRF tokens:

# Flask example
from flask_wtf.csrf import CSRFProtect
csrf = CSRFProtect(app)

# In templates, include the token:
# <input type="hidden" name="csrf_token" value="{{ csrf_token() }}">

# FastAPI — use a middleware or dependency
from fastapi_csrf_protect import CsrfProtect

Alternatively, use the SameSite=Strict cookie attribute — modern browsers enforce this by default.

How CSRF Attacks Work

A user logs into bank.com, receiving a session cookie. They then visit evil.com which contains a hidden form:

<!-- On evil.com -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker-account" />
  <input name="amount" value="10000" />
</form>
<script>document.forms[0].submit()</script>

The browser sends the bank.com cookies with the request because it's targeting bank.com. The CSRF token ensures the request originated from your own site, not a third party.

Secure Authentication

Hash passwords with bcrypt or argon2, never MD5/SHA:

# Python — bcrypt via passlib
from passlib.context import CryptContext
pwd_ctx = CryptContext(schemes=["bcrypt"])

hashed = pwd_ctx.hash("user_password")
is_valid = pwd_ctx.verify("user_password", hashed)

# Node.js — bcrypt
const bcrypt = require('bcrypt');
const hashed = await bcrypt.hash('user_password', 12);
const valid = await bcrypt.compare('user_password', hashed);

For JWT tokens: use short expiry (15 min), store refresh tokens in httpOnly cookies, and implement token rotation.

JWT Best Practices

JWTs are convenient but easy to misuse. Common mistakes:

// DANGEROUS — storing JWT in localStorage (XSS can steal it)
localStorage.setItem('token', jwt);

// SAFE — store in httpOnly cookie (JS can't access)
res.cookie('token', jwt, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict',
  maxAge: 15 * 60 * 1000  // 15 minutes
});

Use access tokens (short-lived, 15 min) for API calls and refresh tokens (longer-lived, 7 days) stored in httpOnly cookies for token renewal. Implement token rotation — each refresh token can only be used once, and using an old one invalidates the entire session.

Rate Limiting Authentication

Prevent brute-force attacks by rate-limiting login attempts:

# Python — slowapi
from slowapi import Limiter
limiter = Limiter(key_func=get_remote_address)

@app.post("/login")
@limiter.limit("5/minute")
async def login(request: Request):
    # ... authentication logic

Implement account lockout after 10 failed attempts, or require CAPTCHA. For APIs, use exponential backoff — each failed attempt increases the delay before the next one is allowed.

Security Headers

Add these headers to every response:

# Caddy (automatic HTTPS + headers)
header {
    Strict-Transport-Security "max-age=31536000; includeSubDomains"
    X-Content-Type-Options "nosniff"
    X-Frame-Options "DENY"
    Referrer-Policy "strict-origin-when-cross-origin"
    Permissions-Policy "camera=(), microphone=(), geolocation=()"
}

# nginx
add_header Strict-Transport-Security "max-age=31536000" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;

What Each Header Does

  • HSTS — forces HTTPS for all future requests, prevents SSL stripping attacks
  • X-Content-Type-Options — prevents MIME sniffing (browser executing a "text file" as JavaScript)
  • X-Frame-Options — prevents clickjacking (your site loaded in a hidden iframe)
  • Referrer-Policy — controls how much referrer info is sent with requests (prevents leaking URLs with tokens)
  • Permissions-Policy — disables browser features your site doesn't need (camera, mic, geolocation)

Dependency Scanning

Your dependencies are your attack surface. Scan regularly:

# npm
npm audit
npx snyk test

# Python
pip-audit
safety check

# In CI/CD (GitHub Actions)
- uses: github/codeql-action/analyze@v3
- uses: snyk/actions/python@master

Supply Chain Security

In 2026, supply chain attacks are the fastest-growing threat vector. Protect yourself:

  • Pin exact dependency versions in package-lock.json / requirements.txt
  • Use npm audit --production to ignore dev-only vulnerabilities in production builds
  • Enable Dependabot or Renovate for automated dependency update PRs
  • Review dependency changes before merging — a package with 2 weekly downloads suddenly getting a new maintainer is a red flag
  • Use npm ci instead of npm install in CI to ensure lockfile integrity

SQL Injection Prevention

Use parameterized queries or an ORM. Never concatenate user input into SQL strings:

# DANGEROUS
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")

# SAFE — parameterized query
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))

# SAFE — ORM (SQLAlchemy)
user = db.query(User).filter(User.id == user_id).first()

ORM Pitfalls

Even ORMs can be vulnerable if you use raw query methods:

# DANGEROUS — SQLAlchemy raw text
db.execute(text(f"SELECT * FROM users WHERE name = '{name}'"))

# SAFE — parameterized
db.execute(text("SELECT * FROM users WHERE name = :name"), {"name": name})

Always use parameter binding, even in ORMs. If you must write raw SQL, use the database driver's parameterized query API.

API Security

If your app exposes APIs, additional security layers are critical:

# Rate limiting with Express
const rateLimit = require('express-rate-limit');

const apiLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,  // 15 minutes
  max: 100,  // limit each IP to 100 requests per window
  standardHeaders: true,
  legacyHeaders: false,
});

app.use('/api/', apiLimiter);

Implement request size limits to prevent denial-of-service via large payloads. In Express, use express.json({ limit: "1mb" }). In FastAPI, configure your ASGI server with max_content_length.

Validate Content-Type headers — reject unexpected formats on endpoints that expect JSON. This prevents parser confusion attacks where data is interpreted differently than intended.

Logging and Monitoring

Security without observability is blind. Log security-relevant events — failed logins, permission denials, data access patterns. Use structured logging with correlation IDs so you can trace an attack across services:

# Structured security logging
import structlog

logger = structlog.get_logger()

def log_auth_event(event_type, user_id, ip, success, reason=None):
    logger.info("auth_event",
        event_type=event_type,
        user_id=user_id,
        ip=ip,
        success=success,
        reason=reason
    )

Monitor for repeated failed logins (brute force), unusual data access patterns (exfiltration), requests from known malicious IPs, and spikes in error rates. Set up alerts for anomalies — catching an attack in progress is far better than discovering it in a post-mortem.

Pro tip:
Pro tip: Run npm audit --production in CI and fail the build on critical vulnerabilities. Set up Dependabot or Renovate for automatic PR updates. Combine with trivy for container image scanning in the same pipeline.

Input Validation

Validate on both client and server. Client-side validation is UX; server-side validation is security:

// Server-side validation with Zod (Node.js)
import { z } from 'zod';

const UserSchema = z.object({
  email: z.string().email().max(255),
  name: z.string().min(1).max(100).regex(/^[a-zA-Z\s]+$/),
  age: z.number().int().min(13).max(150),
});

const result = UserSchema.safeParse(req.body);
if (!result.success) {
  return res.status(400).json({ errors: result.error.issues });
}

For Python, use Pydantic with FastAPI — it validates automatically from type hints. For Go, use go-playground/validator. The key principle: validate at trust boundaries (API entry points, form handlers, webhook receivers), never trust client-side validation alone.

Wrapping Up

Security isn't a feature — it's a requirement. Implement these practices from day one, not after a breach. Every developer should treat OWASP Top 10 as a checklist, not optional reading. Start with the basics: parameterized queries, output encoding, CSP headers, and dependency scanning. Then layer on rate limiting, JWT hardening, and monitoring. Security is a practice, not a destination.
